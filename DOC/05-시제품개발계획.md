## 1. 진행 규칙

### 1.1 한 단계의 크기
- 한 단계는 **한 가지 기능**만 다룬다. 끝나면 실행해서 눈으로 확인할 수 있거나 테스트로 확인할 수 있어야 한다.
- 한 단계는 **커밋 하나**다. 문제가 생기면 그 단계만 되돌릴 수 있다.
- 단계가 예상보다 커지면 그 자리에서 둘로 나눈다.

### 1.2 한 단계의 흐름

```
구현 → 자동 검증 → 직접 확인 항목 제시 → 확인 → 커밋 → 다음 단계
```

- 자동 검증이 실패하면 다음으로 넘어가지 않는다.
- **기본은 단계마다 멈추고 확인을 받는다.** 직접 확인할 것이 없는 단계(순수 로직 등)는 자동 검증 결과만 보고하고 이어서 진행할 수 있다. 멈추는 간격은 진행하면서 조정한다.

### 1.3 완료의 정의
한 단계는 다음을 모두 만족해야 끝난 것이다.

1. 그 단계의 자동 검증이 통과한다.
2. **이전 단계들의 자동 검증도 여전히 통과한다** (`npm run check` 전체).
3. 직접 확인 항목을 확인했다.
4. 브라우저 콘솔에 오류가 없다.
5. 화면에 새로 나온 글자가 영어와 한국어 문구 파일에 모두 있다 (0.10 이후).
6. 커밋했다.

### 1.4 수치의 출처
단계에서 쓰는 수치(속도, 시간, 피해량 등)는 [시제품 설계](06-시제품설계.md) 3장의 값을 쓴다. 수치는 코드 여기저기에 흩지 않고 한 파일에 모아, 조정할 때 그 파일만 고치면 되게 한다. 직접 확인하다가 값을 바꾸면 시제품 설계 문서에도 반영한다.

### 1.5 화면의 출처
화면의 배치, 구성 요소, 키 배치는 [UI 설계](07-UI설계.md)를 따른다. 어느 단계에서 어떤 화면을 만드는지는 그 문서의 14장에 있다. 만들다가 배치를 바꾸면 UI 설계 문서에도 반영한다.

## 2. 검증 수단

3D 게임은 "화면에 제대로 나오는가", "조작감이 좋은가"를 테스트 코드만으로 확인할 수 없다. 그래서 검증을 세 층으로 나눈다.

| 층 | 수단 | 확인하는 것 | 누가 |
|---|---|---|---|
| 자동 | 타입 검사, 빌드, 단위 테스트 | 로직이 맞는가, 깨진 곳이 없는가 | 명령 한 번 |
| 반자동 | 스모크 테스트 (실제 브라우저를 띄워 상태 값과 화면 캡처 확인) | 실행되는가, 오류가 없는가, 상태가 기대대로 바뀌는가 | 명령 한 번 |
| 직접 | 플레이하며 확인 목록 점검 | 보이는 것, 들리는 것, 조작감 | 사람 |

### 2.1 명령

모두 `Src/`에서 실행한다.

| 명령 | 내용 | 도입 단계 |
|---|---|---|
| `npm run typecheck` | 타입 검사 (`tsc --noEmit`) | 0.1 |
| `npm run build` | 배포용 빌드 | 0.1 |
| `npm test` | 단위 테스트 (Vitest) | 0.2 |
| `npm run smoke` | 스모크 테스트 | 0.4 |
| `npm run check` | 위 네 가지를 차례로 실행 | 0.4 |
| `npm run perf:report` | 개발용 성능 로그 요약 (2.4절 ④) | 0.9 |
| `npm run size` | 빌드 결과물의 용량 보고 | 2.26 |

### 2.2 검증하기 쉬운 구조

검증을 쉽게 하려고 처음부터 넣는 장치다.

| 장치 | 내용 | 용도 |
|---|---|---|
| 순수 모듈 분리 | 계산(시간, 날씨, 체온, 가방, 수리 진행)은 Three.js와 브라우저에 의존하지 않는 함수로 작성 | 단위 테스트로 검증 |
| 디버그 객체 | `window.__game`으로 현재 상태를 읽을 수 있게 함 (구역, 플레이어 위치, 체력, 날씨 단계, 엔티티 수, 렌더 통계) | 스모크 테스트가 값을 확인 |
| 시작 조건 지정 | 주소 뒤에 조건을 붙여 특정 상황에서 시작. 예: `?skipIntro`, `?time=18:00`, `?storm=now`, `?timescale=30`, `?seed=1`, `?lang=en` | 폭풍이나 밤을 기다리지 않고 바로 확인 |
| 디버그 화면 | 키 하나로 여닫는 화면. 수치 표시, 폭풍 호출, 시간 이동, 대피 영역 표시 | 직접 확인을 빠르게 |
| 고정 시드 | 난수는 시드를 받는 생성기만 사용 | 같은 조건에서 같은 결과 |
| 수치 파일 | 조정할 수치를 한 파일에 모음 | 값을 바꿔 가며 확인 |

디버그 객체와 디버그 화면은 개발용 빌드에만 넣는다.

### 2.3 스모크 테스트의 동작과 한계

스모크 테스트(`Src/scripts/smoke.mjs`)는 개발 서버를 띄우고, PC에 설치된 Edge 또는 Chrome을 화면 없이 실행해 게임을 연 뒤 다음을 확인한다: 디버그 객체가 준비됨, 캔버스가 있음, 프레임이 계속 그려짐, 콘솔 오류와 실패한 요청이 없음. 화면 캡처는 `Src/test-results/smoke.png`에 남는다. 브라우저를 따로 내려받지 않으므로 Edge나 Chrome이 설치되어 있어야 한다(`SMOKE_BROWSER_CHANNEL` 환경 변수로 지정 가능).

스모크 테스트는 화면 없는 브라우저에서 돌기 때문에 그래픽이 소프트웨어로 처리된다. **성능 수치와 정확한 색은 믿을 수 없다.** "실행되는가, 오류가 없는가, 상태가 맞는가"만 확인하고, 성능과 모습은 직접 확인한다.

### 2.4 성능 측정

성능은 스모크 테스트로 확인할 수 없으므로 게임 안에 측정 기능을 넣는다. 세 가지다.

**① 성능 HUD (개발용, 0.9와 0.12)**

디버그 화면에 항상 표시한다. 예산을 넘는 값은 색을 바꿔 표시한다.

| 항목 | 내용 |
|---|---|
| FPS | 현재, 최근 평균, 하위 1% (가장 느린 프레임들의 평균) |
| 프레임 시간 | 한 프레임을 처리하는 데 걸린 시간(ms), 최근 몇 초의 그래프 |
| 긴 프레임 횟수 | 33ms와 50ms를 넘은 프레임의 수 (끊김으로 느껴지는 순간) |
| 구간별 시간 | 시뮬레이션(물리, 게임 로직)과 렌더에 각각 걸린 시간 |
| 그리는 양 | 드로우콜, 삼각형 수 |
| 자원 수 | 지오메트리, 텍스처, 엔티티 수 (구역을 오가도 늘지 않아야 함) |
| 메모리 | 사용 중인 메모리 (지원하는 브라우저에서만) |
| 구역 전환 시간 | 마지막 전환에 걸린 시간 |

FPS는 모니터 주사율에 막혀 60이나 144에서 멈추기 때문에 여유가 얼마나 있는지 알려 주지 못한다. 그래서 **프레임 시간**을 함께 본다. 60fps의 한 프레임은 16.7ms이므로, 프레임 시간이 8ms라면 절반의 여유가 있다는 뜻이다.

**② 성능 측정 모드 (1.12)**

주소에 `?bench`를 붙이면 정해진 경로를 카메라가 자동으로 지나가며 측정하고 결과를 보여 준다. 사람이 조작하지 않으므로 **언제 측정해도 같은 조건**이 된다.

| 항목 | 내용 |
|---|---|
| 경로 | 마른 강바닥을 한 바퀴 도는 정해진 경로 (약 60초). M2에서 폭풍 구간 추가 |
| 결과 | 평균 FPS, 하위 1% FPS, 최대 프레임 시간, 긴 프레임 횟수, 최대 드로우콜, 최대 삼각형 수, 구간별 평균 시간 |
| 판정 | 성능 예산과 비교해 항목별로 통과/초과 표시 |
| 기기 정보 | 브라우저, 화면 크기, 그래픽 품질 설정, 그래픽 장치 이름 |
| 내보내기 | 결과를 글자로 복사 |

용도는 세 가지다. 변경 전후의 성능 비교, 그래픽 품질 "낮음"과 "높음"의 차이 확인, 다른 PC에서 측정한 결과 받아 보기.

**③ 플레이어용 FPS 표시 (2.22)**

설정에서 켜면 화면 구석에 현재 FPS만 작게 표시한다. 디버그 화면과 달리 배포판에도 들어간다. 테스트하는 사람이 "느리다"고 할 때 실제 수치를 알려 줄 수 있다.

**④ 개발용 성능 로그 (0.9)**

`npm run dev`로 띄운 게임은 5초마다 성능 수치를 개발 서버로 보내고, 서버가 `Src/logs/perf.jsonl`에 한 줄씩 기록한다. 수치를 눈으로 읽어 옮길 필요 없이 로그를 보면 된다.

| 항목 | 내용 |
|---|---|
| 기록 내용 | 접속마다 기기 정보(브라우저, 그래픽 장치 이름, 화면 크기) 한 번, 이후 5초마다 FPS·프레임 시간·긴 프레임 횟수·드로우콜·삼각형·자원 수 |
| 보는 방법 | `npm run perf:report` (접속별 요약). `npm run perf:report -- 3`은 최근 3회만 |
| 기록되지 않는 경우 | 스모크 테스트 같은 자동 실행, 탭이 가려져 있을 때, 처음 60프레임 |
| 범위 | 개발 서버에서만 동작한다. 배포한 게임에는 보낼 서버가 없으므로 들어가지 않는다 |
| 저장소 | `logs/` 폴더는 커밋하지 않는다 |

소프트웨어로 그리는 접속(화면 없는 브라우저)은 요약에 따로 표시된다. 그 수치는 실제 성능이 아니다.

배포한 게임에서 테스트하는 사람의 성능은 이 로그로 볼 수 없다. 그것은 플레이 기록(2.25)의 성능 요약이 맡는다.

**성능 예산** (시제품 기준, [기술 설계서](02-기술설계서.md) 15장)

| 항목 | 낮음 품질 | 높음 품질 |
|---|---|---|
| 평균 FPS | 30 이상 | 60 이상 |
| 하위 1% FPS | 20 이상 | 45 이상 |
| 드로우콜 | 250 이하 | 500 이하 |
| 삼각형 | 30만 이하 | 100만 이하 |
| 50ms를 넘는 프레임 | 측정 중 5회 이하 | 좌동 |

하위 1% FPS와 긴 프레임 횟수의 기준은 이 문서에서 새로 정한 초기값이다.

**측정 기록**: 마일스톤을 끝낼 때마다 성능 측정 모드를 돌리고 결과를 11장에 적는다. 성능이 나빠진 시점을 나중에 찾을 수 있다.

## 3. 로드맵 점검에서 발견한 것

단계를 쪼개면서 드러난 문제와 그에 따른 조정이다.

| # | 발견 | 조정 |
|---|---|---|
| 1 | 로드맵에 검증 방법이 없고, 화면을 확인할 자동 수단이 없었다 | 스모크 테스트와 디버그 장치를 M0에 추가 (0.4) |
| 2 | UI 도구(Preact, Tailwind)는 시제품의 화면에는 과하다 | 시제품은 일반 DOM으로 만들고, 도입은 인벤토리 화면을 만드는 M4로 미룸 |
| 3 | 물리 엔진을 M0에서 설치하지만 M1에서야 쓴다 | 쓰는 단계(1.1)에서 설치 |
| 4 | "플레이 시간 측정"을 어디에 보낼지 정해지지 않았다 | 시제품은 기기 안에만 기록하고 화면에서 확인 (2.25). 공개 테스트용 수집 방법은 G1에서 결정 |
| 5 | 테스트할 사람에게 전달할 방법이 계획에 없었다 | 배포 단계 추가 (2.27) |
| 6 | 폭풍의 느낌에는 소리가 중요한데 M2 목록에 소리가 "표현"의 일부로만 있었다 | 소리를 별도 단계로 분리 (2.6). 무료 음원 확보 필요 |
| 7 | 캐릭터 모델과 애니메이션은 무료 에셋 호환 문제로 시간이 걸릴 수 있다 | 캡슐로 진행하고, 모델 적용은 선택 단계로 분리 (1.11) |
| 8 | 게임패드는 기기가 있어야 확인할 수 있다 | 선택 단계로 분리 (0.8). 입력 구조만 대비해 둠 |
| 9 | 구역 전환 시 메모리 누수는 나중에 발견하면 고치기 어렵다 | 전환을 만드는 단계(2.16)에서 왕복 후 자원 수가 늘지 않는지 자동 확인 |

## 5. M1 — 캐릭터와 구역

### 6.1 시간과 날씨

| 2.1 | **게임 시각.** 하루 8분 시계, 낮/밤 판정, 시작 조건(`?time`, `?timescale`) | 단위 테스트: 경과 시간 → 시각과 날짜, 낮/밤 경계 | HUD에 시각이 표시되고 흐름 |

## 7. 시제품 통합 확인 목록

2.28에서 사용한다. "판단" 항목을 빼고 전부 "예"여야 G1(플레이 테스트)로 넘어간다.

### 흐름
- [ ] 접속하면 타이틀 화면이 뜨고, START 한 번으로 바로 조작할 수 있다
- [ ] 도입부 2분이 끊김 없이 진행되고 대피소에 도착한다
- [ ] 대피소에서 나가 수색하고, 폭풍을 피하고, 돌아와 정산하는 과정을 반복해 문 수리를 끝낼 수 있다
- [ ] 수리를 끝내면 끝 화면이 나오고 의견을 남길 수 있다
- [ ] 죽으면 다음 날 다시 시작하고, 떨어뜨린 가방을 되찾을 수 있다
- [ ] 처음부터 끝까지 10~15분이 걸린다
- [ ] 그동안 오류나 멈춤이 없다

### 전달
- [ ] 폭풍이 온다는 것을 화면 표시를 보기 전에 풍경과 소리로 알 수 있다
- [ ] 건물 안이 안전하다는 것을 설명 없이 알 수 있다
- [ ] 체력이 왜 줄어드는지 알 수 있다 (폭풍, 추위, 갈증이 구분됨)
- [ ] 가방이 가득 찼다는 것을 알 수 있다
- [ ] 무엇을 얼마나 더 모아야 하는지 알 수 있다

### 언어와 설정
- [ ] 영어와 한국어 모두에서 빠진 글자나 깨진 배치가 없다
- [ ] 설정의 모든 항목이 동작하고 새로 고쳐도 유지된다
- [ ] Esc로 멈췄다가 돌아와도 조작이 정상이다

### 기술
- [ ] 성능 측정 모드의 결과가 높음 품질에서 예산 안이다 (개발 PC 기준)
- [ ] 성능 측정 모드의 결과가 낮음 품질에서 예산 안이다 (최소 사양 기기가 있을 때)
- [ ] 10분 플레이 후 자원 수(지오메트리, 텍스처, 엔티티)가 처음과 비슷하다
- [ ] 측정 결과를 11장에 기록했다
- [ ] 구역 전환이 2초 안이다
- [ ] 시작 묶음이 10MB 이하이고 10초 안에 조작할 수 있다
- [ ] Chrome, Edge, Firefox에서 실행된다 (Safari는 기기가 있을 때)
- [ ] `npm run check`가 통과한다

### 판단 (정답이 없는 항목)
- [ ] 폭풍이 올 때 긴장되는가, 귀찮은가
- [ ] "한 번만 더 나가 볼까"라는 생각이 드는가
- [ ] 상자를 하나 더 열지 고민한 순간이 있었는가

마지막 세 항목은 만든 사람의 판단이므로 참고만 한다. 실제 답은 G1에서 다른 사람이 준다.

## 8. 단계 수와 의존 관계

| 구간 | 단계 수 | 선택 단계 |
|---|---|---|
| M0 | 12 | 0.8 (게임패드) |
| M1 | 14 | 1.11 (캐릭터 모델) |
| M2 | 28 | — |
| 합계 | 54 | 2 |

- M0 → M1 → M2 순서로 진행한다.
- M2 안에서는 6.1(시간·날씨) → 6.2(생존) → 6.3(수색과 목표) → 6.4(흐름) → 6.5(마무리) 순서다.
- 6.2와 6.3은 서로 독립적이어서 순서를 바꿀 수 있다. 다만 2.15(물건 사용)는 2.10(갈증)이, 2.19(폭풍 뒤 물건)는 2.3(날씨 상태)이 먼저 있어야 한다.
- 2.6(소리)은 음원 확보가 늦어지면 뒤로 미룰 수 있다. 2.22(설정의 음량)와 2.23(도입부) 전에는 있어야 한다.
- 2.22(설정 메뉴)는 2.21(일시정지)에서 들어간다.
