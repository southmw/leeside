## 1. 진행 규칙

### 1.1 한 단계의 크기
- 한 단계는 **한 가지 기능**만 다룬다. 끝나면 실행해서 눈으로 확인할 수 있거나 테스트로 확인할 수 있어야 한다.
- 한 단계는 **커밋 하나**다. 문제가 생기면 그 단계만 되돌릴 수 있다.
- 단계가 예상보다 커지면 그 자리에서 둘로 나눈다.

### 1.2 한 단계의 흐름

```
구현 → 자동 검증 → 직접 확인 항목 제시 → 확인 → 커밋 → 다음 단계
```

- 자동 검증이 실패하면 다음으로 넘어가지 않는다.
- **기본은 단계마다 멈추고 확인을 받는다.** 직접 확인할 것이 없는 단계(순수 로직 등)는 자동 검증 결과만 보고하고 이어서 진행할 수 있다. 멈추는 간격은 진행하면서 조정한다.

### 1.3 완료의 정의
한 단계는 다음을 모두 만족해야 끝난 것이다.

1. 그 단계의 자동 검증이 통과한다.
2. **이전 단계들의 자동 검증도 여전히 통과한다** (`npm run check` 전체).
3. 직접 확인 항목을 확인했다.
4. 브라우저 콘솔에 오류가 없다.
5. 화면에 새로 나온 글자가 영어와 한국어 문구 파일에 모두 있다 (0.10 이후).
6. 커밋했다.

### 1.4 수치의 출처
단계에서 쓰는 수치(속도, 시간, 피해량 등)는 [시제품 설계](06-시제품설계.md) 3장의 값을 쓴다. 수치는 코드 여기저기에 흩지 않고 한 파일에 모아, 조정할 때 그 파일만 고치면 되게 한다. 직접 확인하다가 값을 바꾸면 시제품 설계 문서에도 반영한다.

### 1.5 화면의 출처
화면의 배치, 구성 요소, 키 배치는 [UI 설계](07-UI설계.md)를 따른다. 어느 단계에서 어떤 화면을 만드는지는 그 문서의 14장에 있다. 만들다가 배치를 바꾸면 UI 설계 문서에도 반영한다.

## 2. 검증 수단

3D 게임은 "화면에 제대로 나오는가", "조작감이 좋은가"를 테스트 코드만으로 확인할 수 없다. 그래서 검증을 세 층으로 나눈다.

| 층 | 수단 | 확인하는 것 | 누가 |
|---|---|---|---|
| 자동 | 타입 검사, 빌드, 단위 테스트 | 로직이 맞는가, 깨진 곳이 없는가 | 명령 한 번 |
| 반자동 | 스모크 테스트 (실제 브라우저를 띄워 상태 값과 화면 캡처 확인) | 실행되는가, 오류가 없는가, 상태가 기대대로 바뀌는가 | 명령 한 번 |
| 직접 | 플레이하며 확인 목록 점검 | 보이는 것, 들리는 것, 조작감 | 사람 |

### 2.1 명령

모두 `Src/`에서 실행한다.

| 명령 | 내용 | 도입 단계 |
|---|---|---|
| `npm run typecheck` | 타입 검사 (`tsc --noEmit`) | 0.1 |
| `npm run build` | 배포용 빌드 | 0.1 |

### 2.2 검증하기 쉬운 구조

검증을 쉽게 하려고 처음부터 넣는 장치다.

| 장치 | 내용 | 용도 |
|---|---|---|
| 순수 모듈 분리 | 계산(시간, 날씨, 체온, 가방, 수리 진행)은 Three.js와 브라우저에 의존하지 않는 함수로 작성 | 단위 테스트로 검증 |
| 디버그 객체 | `window.__game`으로 현재 상태를 읽을 수 있게 함 (구역, 플레이어 위치, 체력, 날씨 단계, 엔티티 수, 렌더 통계) | 스모크 테스트가 값을 확인 |
| 시작 조건 지정 | 주소 뒤에 조건을 붙여 특정 상황에서 시작. 예: `?skipIntro`, `?time=18:00`, `?storm=now`, `?timescale=30`, `?seed=1`, `?lang=en`, `?at=150,160&face=270` | 폭풍이나 밤을 기다리지 않고 바로 확인 |
| 디버그 화면 | 키 하나로 여닫는 화면. 수치 표시, 폭풍 호출, 시간 이동, 대피 영역 표시 | 직접 확인을 빠르게 |
| 고정 시드 | 난수는 시드를 받는 생성기만 사용 | 같은 조건에서 같은 결과 |
| 수치 파일 | 조정할 수치를 한 파일에 모음 | 값을 바꿔 가며 확인 |

디버그 객체와 디버그 화면은 개발용 빌드에만 넣는다.

### 2.3 스모크 테스트의 동작과 한계

스모크 테스트(`Src/scripts/smoke.mjs`)는 개발 서버를 띄우고, PC에 설치된 Edge 또는 Chrome을 화면 없이 실행해 게임을 연 뒤 다음을 확인한다: 디버그 객체가 준비됨, 캔버스가 있음, 프레임이 계속 그려짐, 콘솔 오류와 실패한 요청이 없음. 화면 캡처는 `Src/test-results/smoke.png`에 남는다. 브라우저를 따로 내려받지 않으므로 Edge나 Chrome이 설치되어 있어야 한다(`SMOKE_BROWSER_CHANNEL` 환경 변수로 지정 가능).

스모크 테스트는 화면 없는 브라우저에서 돌기 때문에 그래픽이 소프트웨어로 처리된다. **성능 수치와 정확한 색은 믿을 수 없다.** "실행되는가, 오류가 없는가, 상태가 맞는가"만 확인하고, 성능과 모습은 직접 확인한다.

### 2.4 성능 측정

성능은 스모크 테스트로 확인할 수 없으므로 게임 안에 측정 기능을 넣는다. 세 가지다.

**① 성능 HUD (개발용, 0.9와 0.12)**

디버그 화면에 항상 표시한다. 예산을 넘는 값은 색을 바꿔 표시한다.

| 항목 | 내용 |
|---|---|
| FPS | 현재, 최근 평균, 하위 1% (가장 느린 프레임들의 평균) |
| 프레임 시간 | 한 프레임을 처리하는 데 걸린 시간(ms), 최근 몇 초의 그래프 |
| 긴 프레임 횟수 | 33ms와 50ms를 넘은 프레임의 수 (끊김으로 느껴지는 순간) |
| 구간별 시간 | 시뮬레이션(물리, 게임 로직)과 렌더에 각각 걸린 시간 |
| 그리는 양 | 드로우콜, 삼각형 수 |
| 자원 수 | 지오메트리, 텍스처, 엔티티 수 (구역을 오가도 늘지 않아야 함) |
| 메모리 | 사용 중인 메모리 (지원하는 브라우저에서만) |
| 구역 전환 시간 | 마지막 전환에 걸린 시간 |

FPS는 모니터 주사율에 막혀 60이나 144에서 멈추기 때문에 여유가 얼마나 있는지 알려 주지 못한다. 그래서 **프레임 시간**을 함께 본다. 60fps의 한 프레임은 16.7ms이므로, 프레임 시간이 8ms라면 절반의 여유가 있다는 뜻이다.

**② 성능 측정 모드 (1.12)**

주소에 `?bench`를 붙이면 정해진 경로를 카메라가 자동으로 지나가며 측정하고 결과를 보여 준다. 사람이 조작하지 않으므로 **언제 측정해도 같은 조건**이 된다.

| 항목 | 내용 |
|---|---|
| 경로 | 마른 강바닥을 한 바퀴 도는 정해진 경로 (약 60초). M2에서 폭풍 구간 추가 |
| 결과 | 평균 FPS, 하위 1% FPS, 최대 프레임 시간, 긴 프레임 횟수, 최대 드로우콜, 최대 삼각형 수, 구간별 평균 시간 |
| 판정 | 성능 예산과 비교해 항목별로 통과/초과 표시 |
| 기기 정보 | 브라우저, 화면 크기, 그래픽 품질 설정, 그래픽 장치 이름 |
| 내보내기 | 결과를 글자로 복사 |

용도는 세 가지다. 변경 전후의 성능 비교, 그래픽 품질 "낮음"과 "높음"의 차이 확인, 다른 PC에서 측정한 결과 받아 보기.

**③ 플레이어용 FPS 표시 (2.22)**

설정에서 켜면 화면 구석에 현재 FPS만 작게 표시한다. 디버그 화면과 달리 배포판에도 들어간다. 테스트하는 사람이 "느리다"고 할 때 실제 수치를 알려 줄 수 있다.

**④ 개발용 성능 로그 (0.9)**

`npm run dev`로 띄운 게임은 5초마다 성능 수치를 개발 서버로 보내고, 서버가 `Src/logs/perf.jsonl`에 한 줄씩 기록한다. 수치를 눈으로 읽어 옮길 필요 없이 로그를 보면 된다.

| 항목 | 내용 |
|---|---|
| 기록 내용 | 접속마다 기기 정보(브라우저, 그래픽 장치 이름, 화면 크기) 한 번, 이후 5초마다 FPS·프레임 시간·긴 프레임 횟수·드로우콜·삼각형·자원 수 |
| 보는 방법 | `npm run perf:report` (접속별 요약). `npm run perf:report -- 3`은 최근 3회만 |
| 기록되지 않는 경우 | 스모크 테스트 같은 자동 실행, 탭이 가려져 있을 때, 처음 60프레임 |
| 범위 | 개발 서버에서만 동작한다. 배포한 게임에는 보낼 서버가 없으므로 들어가지 않는다 |
| 저장소 | `logs/` 폴더는 커밋하지 않는다 |

소프트웨어로 그리는 접속(화면 없는 브라우저)은 요약에 따로 표시된다. 그 수치는 실제 성능이 아니다.

배포한 게임에서 테스트하는 사람의 성능은 이 로그로 볼 수 없다. 그것은 플레이 기록(2.25)의 성능 요약이 맡는다.

**성능 예산** (시제품 기준, [기술 설계서](02-기술설계서.md) 15장)

| 항목 | 낮음 품질 | 높음 품질 |
|---|---|---|
| 평균 FPS | 30 이상 | 60 이상 |
| 하위 1% FPS | 20 이상 | 45 이상 |
| 드로우콜 | 250 이하 | 500 이하 |
| 삼각형 | 30만 이하 | 100만 이하 |
| 50ms를 넘는 프레임 | 측정 중 5회 이하 | 좌동 |

하위 1% FPS와 긴 프레임 횟수의 기준은 이 문서에서 새로 정한 초기값이다.

**측정 기록**: 마일스톤을 끝낼 때마다 성능 측정 모드를 돌리고 결과를 11장에 적는다. 성능이 나빠진 시점을 나중에 찾을 수 있다.

## 5. M1 — 캐릭터와 구역

완료 기준: 임시 도형으로 만든 구역 하나를 돌아다니고 건물에 들어갈 수 있음

| 단계 | 내용 | 자동 검증 | 직접 확인 |
|---|---|---|---|
| 1.1 | **물리 연결.** Rapier 설치와 초기화, 루프에 물리 스텝 연결, 바닥 충돌체, 떨어지는 상자 | 단위 테스트: 상자가 일정 틱 뒤 바닥 높이에서 멈춤 | 상자가 떨어져 바닥에 멈춤 |
| 1.2 | **캐릭터 이동.** 캡슐 캐릭터, 한 가지 속도(처음 6.5 m/s, 1.10에서 12 m/s로 변경), 벽에 막힘 | 단위 테스트: 이동 입력 N틱 → 이동 거리 ≈ 속도 × 시간. 벽 너머로 못 감 | 캡슐이 움직이고 상자에 막힘 |
| 1.3 | **점프, 중력, 경사.** | 단위 테스트: 점프 높이 ≈ 1.1m, 착지. 45° 이하는 오르고 그 이상은 못 오름. 공중에서 다시 점프 불가 | 점프 높이와 낙하 속도가 자연스러움 |
| 1.4 | **3인칭 카메라.** 캐릭터 추적, 마우스 회전(처음에는 클릭해서 잡는 방식, 1.11 뒤에 버튼을 누르고 있는 동안만 도는 방식으로 변경), 이동 방향을 카메라 기준으로 | 단위 테스트: 상하 각도 제한, 카메라 방향 기준 이동 벡터 계산 | 마우스로 시점을 돌리고, 보는 방향으로 걸어감 |
| 1.5 | **카메라 벽 보정.** 캐릭터와 카메라 사이가 막히면 카메라를 당김 | 단위 테스트: 장애물 거리 → 카메라 거리 계산 | 벽을 등지면 카메라가 벽을 뚫지 않음 |
| 1.6 | **렌더 보간.** 직전 틱과 현재 틱 사이를 보간해 표시 | 단위 테스트: 보간 함수 | 달릴 때 캐릭터와 배경이 떨리지 않음 |
| 1.7 | **구역 정의 형식.** 구역 정의의 형식과 검증기(`zod`) | 단위 테스트: 올바른 정의는 통과. 필수 항목 누락, 범위 밖 좌표, 중복 ID는 거부 | — |

- M0 → M1 → M2 순서로 진행한다.
- M2 안에서는 6.0(에셋) → 6.1(시간·날씨) → 6.2(생존) → 6.3(수색과 목표) → 6.4(흐름) → 6.5(마무리) 순서다.
- 6.2와 6.3은 서로 독립적이어서 순서를 바꿀 수 있다. 다만 2.15(물건 사용)는 2.10(갈증)이, 2.19(폭풍 뒤 물건)는 2.3(날씨 상태)이 먼저 있어야 한다.
- 6.0(에셋)을 먼저 하는 것은 상자와 물건(2.13, 2.14)을 만들기 전에 스타일을 정해 두기 위해서다. 2.30과 2.31은 상자 수색(2.14) 전까지만 하면 된다. 2.31은 Kenney 팩을 내려받아야 시작할 수 있다.
- 2.6(소리)은 음원 확보가 늦어지면 뒤로 미룰 수 있다. 2.22(설정의 음량)와 2.23(도입부) 전에는 있어야 한다.
- 2.22(설정 메뉴)는 2.21(일시정지)에서 들어간다.

## 11. 성능 측정 기록

마일스톤을 끝낼 때마다 성능 측정 모드(`?bench`)의 결과를 적는다. 같은 PC에서 측정해야 비교할 수 있으므로 기기를 함께 적는다.

1.12의 측정(60초, 3,600프레임)에서 평균 프레임 시간은 16.7ms, 34ms를 넘는 프레임은 없었고, 프레임당 시뮬레이션 0.32ms, 렌더(CPU) 0.57ms였다. 모니터 주사율(60Hz)에 막힌 수치라서, 실제 여유는 구간별 시간으로 본다: 한 프레임 16.7ms 중 게임 코드가 쓰는 시간은 1ms가 안 된다. 한 번 측정한 값이다.

2.30의 측정에서 차량 모델 4대는 드로우콜을 19, 삼각형을 약 2만 5천 늘렸지만 평균 FPS와 프레임당 렌더 시간(0.44 → 0.50ms)은 거의 같았다. 다만 처음에는 60초 동안 두 번, 최대 200ms 멈췄다. 모델이 처음 화면에 들어올 때 셰이더 컴파일과 도형·텍스처 전송이 몰린 것으로 보고(차 모델이 2종이고 긴 프레임도 2개), 로딩 중에 구역 전체를 한 번 그려 두게 했더니(`warmUpScene`) 긴 프레임이 없어졌다. 1.12와는 화면 크기가 달라(그리는 크기 2880×1546) 그 줄과 바로 비교할 수는 없다. 각각 한 번 측정한 값이다.

2.31에서 바위와 컨테이너가 모델로 바뀌면서 삼각형이 13만 6천에서 29만으로 늘었지만(예산 100만) 프레임 시간은 그대로였다. 이 측정은 1.12와 같은 화면 크기다.

2.2의 측정에서는 60초 동안 긴 프레임이 한 번(66ms) 있었다. 예산(50ms 초과 5회까지) 안이고 한 번 측정한 값이라 원인은 알 수 없다. 하늘을 넣기 전의 측정(2.31)과는 화면 크기가 달라 바로 비교할 수 없다. 다음 측정에서도 나오면 원인을 찾는다. 프레임당 시뮬레이션 0.42ms, 렌더(CPU) 0.69ms.

2.5부터 측정의 뒤 절반에 예고와 폭풍이 들어간다(벽, 모래 입자 3,000개, 짧은 시야). 폭풍을 넣고도 긴 프레임이 없었고 프레임당 렌더(CPU)는 0.52ms였다. 2.2의 측정에서 한 번 나왔던 긴 프레임(66ms)은 이번에는 나오지 않았다. 같은 화면 크기인 2.31의 측정과 비교하면 드로우콜이 49에서 51로 늘었을 뿐이다.

2.24까지 만든 뒤의 측정(2026-11-24)은 예산 안이었다. 폭풍이 들어간 측정을 큰 화면(그리는 크기 2880×1546)에서 잰 것은 처음이다. 34ms를 넘는 프레임은 없었고 가장 긴 프레임이 33.4ms(주사율 한 번을 놓친 것)여서 하위 1% FPS가 51.9로 나왔다(예산 45). 프레임당 시뮬레이션 0.31ms, 렌더(CPU) 0.57ms로 2.5 때와 같다: 2.7~2.24에서 더한 것(생존 수치, HUD, 가방, 구역, 도입부)은 프레임 시간에 보이지 않는다. 드로우콜은 51에서 54로 늘었다(덮개 등). 하루 전의 측정 한 번은 하위 1% FPS 33.1로 예산 초과였는데, 로그를 보니 측정 중 화면이 네 번 그려지지 않았고(창이 가려진 것으로 보임) 긴 프레임이 모두 그 직후여서 표에 적지 않았다. 한 번 측정한 값이다.

같은 날 품질 "낮음"으로도 쟀다(2.22의 확인 항목). 낮음은 그리는 크기를 화면의 1배로 낮추므로 2880×1546이 1920×1031이 되어 그리는 픽셀이 절반 아래(44%)로 줄고, 모래 입자가 40%로 준다. 가장 긴 프레임이 33.4ms에서 18.9ms로, 하위 1% FPS가 51.9에서 58.3으로 올랐다: 높음에서 주사율을 가끔 놓치던 것이 없어졌다. 평균 FPS와 게임 코드가 쓰는 시간(시뮬레이션 0.31ms, 렌더 0.59ms)은 같다. 즉 이 기기에서 높음의 여유를 줄이는 것은 그리는 픽셀 수이고, 낮음이 그것을 덜어 준다. **삼각형 291,308개는 낮음의 예산(30만)에 거의 닿아 있다.** 낮음은 삼각형을 줄이지 않으므로, 구역에 모델이 조금만 늘어도 낮음에서 예산을 넘는다. 예산을 올릴지, 낮음에서 바위 모델을 단순한 도형으로 바꿀지는 모델을 더 넣는 단계에서 정한다. 각각 한 번 측정한 값이다.

2.28의 측정(2026-11-24)은 사용자가 띄운 화면에서 돌렸고 값은 개발용 로그에서 읽었다. 로그는 5초마다 그때의 최근 300프레임을 요약해 적으므로, 표의 하위 1% FPS는 측정 전체의 값이 아니라 **구간들의 가운데 값**이다(앞의 줄들은 측정 결과 화면의 전체 값이라 그대로 견줄 수 없다). 두 측정 모두 34ms를 넘은 프레임이 없었고 가장 긴 프레임이 33ms대(주사율을 한 번 놓친 것)였다. 그런 프레임이 몰린 구간에서 구간의 하위 1%가 30~36까지 내려갔다. 2.24 뒤의 측정과 같은 모습이다. 낮음으로 적은 줄은 품질이 로그에 없어 미루어 본 것이다: 그 화면은 배율이 1이라 높음과 낮음의 그리는 크기가 같고, 그 PC의 개발 주소에 보관된 설정이 낮음이었다. 문 수리까지의 플레이에서 50ms를 넘은 7번은 측정 모드에는 없는 일(구역 전환, 창 열기)에서 난 것으로 보이며 원인을 따로 찾지는 않았다.
