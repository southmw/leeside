## 1. 설계 목표와 제약

| 목표 | 기준 |
|---|---|
| 대상 플랫폼 | 데스크톱 웹 브라우저 (Chrome, Edge, Firefox, Safari 최신 버전). 모바일은 지원하지 않음 |
| 최소 사양 | 내장 그래픽 노트북에서 낮음 품질로 30fps 이상 |
| 권장 사양 | 외장 그래픽 PC에서 높음 품질로 60fps |
| 장기 확장성 | 아이템·적·레시피를 코드 수정 없이 추가 |
| 초기 로딩 | 첫 화면까지 내려받는 용량을 작게 유지, 나머지는 필요할 때 로드 |
| 첫 플레이까지의 시간 | 접속 후 10초 안에 조작 가능 (일반적인 광대역 회선 기준) |

모바일을 제외하고 오픈월드를 구역 단위로 바꾸면서 큰 기술 리스크는 대부분 사라졌다. 남은 과제는 **첫 로딩과 구역 전환을 짧게 유지하는 것**이다. 많은 사람이 플레이하는 것이 목적이므로, 시작하기 전에 떠나는 사람을 줄이는 것이 성능보다 중요하다. 기술보다 큰 리스크는 개발 범위다(17장).

## 2. 기술 스택

| 영역 | 선택 | 선택 이유 |
|---|---|---|
| 빌드 | Vite + TypeScript (strict) | 빠른 개발 서버, 워커·WASM 지원 |
| 렌더링 | Three.js, `WebGLRenderer` | 브라우저 호환 범위가 넓고 자료가 많음. WebGPU는 이후 검토 |
| 물리 | Rapier (`@dimforge/rapier3d-compat`) | WASM 기반으로 빠르고 캐릭터 컨트롤러 내장 |
| 엔티티 구조 | ECS (`miniplex`) | 시스템이 많아질수록 결합도를 낮게 유지 |
| UI | DOM 오버레이 (Preact + Tailwind CSS) | 인벤토리·제작처럼 목록이 많은 화면에 적합 |
| 데이터 검증 | `zod` | JSON 데이터 오류를 로딩 시점에 발견 |
| 저장 | IndexedDB (`idb-keyval`) | localStorage보다 용량이 크고 비동기 |
| 사운드 | Howler.js | 브라우저의 자동 재생 제한 처리, 교차 재생 지원 |
| 지형 노이즈 | `simplex-noise` | 구역 하이트맵의 바탕을 만드는 개발 도구에서 사용 (게임 실행 중에는 쓰지 않음) |
| 에셋 파이프라인 | `gltf-transform` (meshopt, KTX2) | 모델·텍스처 용량 절감 |
| 테스트 | Vitest | 순수 로직 단위 테스트 |

버전은 설치 시점의 최신 안정 버전을 쓰고 `package-lock.json`으로 고정한다.

## 3. 전체 구조

```
┌─────────────────────────────────────────────────────────┐
│  UI 계층 (Preact, DOM)   HUD · 인벤토리 · 제작 · 메뉴      │
└───────────────▲─────────────────────────┬───────────────┘
                │ 상태 구독                │ 명령
┌───────────────┴─────────────────────────▼───────────────┐
│  게임플레이 계층 (순수 TypeScript, Three.js 비의존)        │
│  전투 · 생존 · 환경 · 인벤토리 · 제작 · 루트 · 성장 · AI   │
└───────────────▲─────────────────────────┬───────────────┘
                │                         │
┌───────────────┴─────────────────────────▼───────────────┐
│  엔진 계층   게임 루프 · ECS · 입력 · 물리 · 구역 로딩      │
└───────────────▲─────────────────────────┬───────────────┘
                │                         │
┌───────────────┴─────────────────────────▼───────────────┐
│  렌더 계층 (Three.js)   씬 · 카메라 · 조명 · 품질 설정      │
└─────────────────────────────────────────────────────────┘
```

### 핵심 원칙
1. **게임 로직과 렌더링 분리** — 피해 계산, 인벤토리, 제작 판정은 Three.js를 import하지 않는 순수 모듈로 작성한다. 테스트하기 쉽고 렌더러를 바꿔도 영향이 없다.
2. **데이터 주도** — 아이템, 레시피, 적, 루트 테이블은 JSON으로 정의한다.
3. **UI는 게임 상태를 읽기만** — UI는 상태를 구독하고, 변경은 명령(예: `craft(recipeId)`)으로만 요청한다.
4. **멀티플레이를 나중에 넣을 수 있게** — 지금은 싱글플레이만 만들지만, 플레이어가 한 명이라는 가정을 코드에 심지 않는다(18장).

## 5. 게임 루프

고정 타임스텝 방식을 쓴다. 기기 성능과 관계없이 물리와 게임 로직이 같은 속도로 진행된다.

```
매 프레임:
  누적 시간 += 지난 프레임 시간 (상한 0.25초)
  while 누적 시간 >= 1/60초:
      입력 반영 → AI → 물리 스텝 → 게임플레이 시스템
      누적 시간 -= 1/60초
  보간 비율 = 누적 시간 / (1/60초)
  렌더 (이전 상태와 현재 상태를 보간)
```

- 시뮬레이션: 60Hz 고정
- 렌더: 화면 주사율에 맞춤, 위치는 보간해서 부드럽게 표시
  - 직전 틱의 위치는 컴포넌트가 아니라 렌더 동기화(`render/renderSync.ts`)가 가진다. 그리는 데만 쓰이고 저장하거나 전송할 상태가 아니기 때문이다. 틱이 시작될 때 기억하고(`capture`), 그릴 때 보간 비율로 섞는다. 순간 이동 뒤에는 `snap`으로 기억을 지운다.
  - 시점(카메라 방향)은 보간하지 않는다. 다음 틱에 반영될 마우스 움직임을 그릴 때 미리 더해, 마우스 반응이 늦어지지 않게 한다.
- 탭이 백그라운드로 가면 일시정지

### 시스템 실행 순서
`입력 → 환경(시간·날씨) → AI → 이동 → 물리 → 전투 → 생존 → 구역 전환 확인 → 정리 → 렌더 동기화`

## 6. ECS 설계

엔티티는 컴포넌트의 묶음이고, 시스템은 특정 컴포넌트를 가진 엔티티를 매 틱 처리한다.

### 주요 컴포넌트

| 컴포넌트 | 내용 | 사용처 |
|---|---|---|
| `transform` | 위치, 회전 | 모든 엔티티 |
| `renderable` | Three.js 객체 참조 | 렌더 동기화 |
| `body` | Rapier 강체/충돌체 핸들 | 물리 |
| `controller` | 이동 의도, 속도, 접지 여부 | 플레이어, 적 |
| `health` | 현재/최대 체력 | 플레이어, 적 |
| `stamina` | 현재/최대 스태미나 | 플레이어 |
| `survival` | 허기, 갈증 | 플레이어 |
| `bodyTemp` | 체온 값, 젖음 정도, 현재 단계 | 플레이어 |
| `insulation` | 장착 복장의 보온·통풍 합계 | 플레이어 |
| `heatSource` | 열량, 반경 | 모닥불, 난로, 횃불 |
| `shelterZone` | 대피 영역(실내·은신처)의 범위와 차단 정도 | POI 건물, 임시 은신처 |
| `combatant` | 공격 상태, 콤보 단계, 무적 시간 | 플레이어, 적 |
| `ai` | 현재 상태, 목표, 감지 범위 | 적 |
| `inventory` | 칸 배열 | 플레이어, 컨테이너 |
| `equipment` | 무기, 방어구 슬롯 | 플레이어 |
| `lootable` | 루트 테이블 ID, 열림 여부 | 컨테이너, 시체 |
| `interactable` | 상호작용 종류, 범위 | 컨테이너, 설비, 아이템 |
| `zoneOwned` | 구역 정의에서의 ID | 구역 해제 시 정리 대상, 구역 상태 저장 대상 |
| `zoneExit` | 연결된 구역과 진입 지점 | 출입구 |
| `travelPoint` | 이동 거점 ID, 활성화 여부 | 이동 거점 |

## 7. 입력 시스템

기기별 입력을 **행동(Action)** 으로 변환해 게임 로직이 기기를 모르게 한다.

```
키보드/마우스 ─┬─→ 입력 매핑 ─→ { move: Vec2, look: Vec2, attack, aim, dodge, jump, interact, ... }
게임패드     ─┘
```

- 키보드/마우스: 포인터 잠금으로 마우스 카메라 조작
- 게임패드: 브라우저 Gamepad API 사용. 마지막으로 쓴 기기에 맞춰 화면의 버튼 안내를 바꾼다.
- 키 설정 변경을 나중에 추가할 수 있도록 매핑 표를 데이터로 둔다.

## 8. 물리와 캐릭터

- Rapier는 `src/physics/`의 `PhysicsWorld`로 감싼다. 게임의 다른 부분은 Rapier 객체를 직접 다루지 않고 물체 번호(핸들)만 가진다. `body` 컴포넌트에는 이 번호만 들어가므로 컴포넌트가 단순한 데이터로 남는다.
- Rapier는 WebAssembly라서 시작할 때 불러오는 과정(`initPhysics`)이 끝난 뒤에 월드를 만든다.
- 물리 스텝은 고정 타임스텝 안에서 한 틱에 한 번 실행한다. 물리 시스템이 스텝 뒤에 물체의 위치를 엔티티의 `transform`에 쓰고, 엔티티가 사라지면 물체를 제거한다.
- `transform`은 세로축 회전만 가지므로 물체의 기울기는 화면에 반영하지 않는다. 시제품에는 구르는 물체가 없어서 충분하다.
- 중력 같은 수치는 `src/data/tuning.ts`에 모은다.
- 캐릭터는 힘이 아니라 위치로 움직이는 물체(kinematic)다. 이동 시스템(`src/gameplay/movementSystem.ts`)이 `input`에서 이번 틱에 가려는 거리를 계산하고, `PhysicsWorld.moveCharacter`가 장애물에 맞게 줄이거나 표면을 따라 꺾는다. 틱 안의 순서는 입력 → 이동 → 물리 스텝이다.
- 점프와 낙하는 순수 모듈(`src/gameplay/verticalMotion.ts`)이 계산하고, 캐릭터의 수직 속도와 착지 여부는 `character` 컴포넌트에 둔다. 경사 제한과 지면 붙기는 캐릭터 컨트롤러의 설정이다.
- 캐릭터 컨트롤러를 쓸 때의 주의점(Rapier 0.21에서 측정):
  - 물체를 추가하거나 제거한 뒤에는 다음 물리 스텝이 지나야 충돌 조회에 반영된다. 그 전에 캐릭터를 움직이면 새 물체를 통과하거나 표면 안쪽으로 들어가 계속 가라앉는다. `PhysicsWorld`가 이 구간에는 캐릭터 이동을 거절한다.
  - 땅에 선 캐릭터를 매 틱 아래로 누르지 않는다. 누르면 이동이 빠지고 바닥으로 가라앉는다. 땅에 있을 때는 수직 이동을 0으로 두고 지면 붙기에 맡기며, 컨트롤러가 땅이 없다고 알리면 그때부터 낙하를 계산한다.
  - 컨트롤러가 알려 주는 "땅에 닿음"을 그대로 믿지 않는다. 가파른 면에 기대어 있거나 공중에서 벽에 밀착해 있어도 닿았다고 알려 주기 때문이다. `PhysicsWorld`가 캡슐을 아래로 짧게 쓸어 실제로 닿은 면이 있고 그 기울기가 제한 이하일 때만 땅으로 판정한다.
  - 공중의 캐릭터는 부딪힌 것에 의해 위로 밀려 올라가지 않게 한다. 캡슐의 둥근 아랫면이 모서리나 가파른 경사를 타고 올라가 점프 높이가 늘어나는 것을 막기 위해서다. 그래도 둥근 아랫면 때문에 실제로 올라갈 수 있는 높이는 점프 높이보다 약 0.1m 높다.
- Rapier의 `KinematicCharacterController`로 플레이어와 적을 이동시킨다. 경사 제한, 계단 오르기, 바닥 붙기를 기본 제공한다.
- 지형은 구역당 충돌체 하나, 구조물은 단순화한 박스/메시 충돌체를 쓴다. 시제품의 지형 충돌체는 높이 격자에서 만든 삼각형 메시다. 화면의 메시, 충돌체, 높이 조회 함수가 같은 삼각형을 쓰므로 서로 어긋나지 않는다(`src/world/terrain.ts`). Rapier의 하이트필드 전용 형식은 칸을 삼각형으로 나누는 방향을 맞추기 어려워 쓰지 않았다. 구역이 커지거나 성능이 문제가 되면 다시 검토한다.
- **공격 판정**: 공격 애니메이션의 유효 구간 동안 무기 앞쪽에 도형 겹침 검사(shape cast)를 수행한다. 한 번의 공격이 같은 대상을 두 번 맞히지 않도록 맞은 대상을 기록한다.
- **카메라**: 플레이어 뒤에서 따라가고, 플레이어에서 카메라 쪽으로 작은 구를 쓸어 보내 벽이나 바닥에 막히면 그 앞까지만 당겨 온다. 어깨 지점(오른쪽으로 치우친 기준점)도 같은 방식으로 벽 밖에 둔다. 다시 멀어질 때는 서서히 움직인다. 당길 때는 카메라 자리 자체가 물체 안이면 즉시, 시야만 가려졌으면 미끄러지듯 다가간다(스쳐 가는 물체에 화면이 튀지 않게).
- **캐릭터의 방향**: 몸이 바라보는 방향은 `character.facing`에 두고 이동하는 방향으로 일정한 속도로 돌린다. 물리 월드의 캡슐은 돌지 않으므로, 물리 시스템이 이 값을 `transform.rotationY`에 넣는다. 시점(카메라 방향)과는 별개다.
- **캐릭터 모델**: 고를 수 있는 캐릭터의 목록(파일, 쓰는 동작의 이름, 달리기 동작의 기준 속도)은 Three.js에 의존하지 않는 데이터로 둔다(`render/characterCatalog.ts`). 타이틀이 이 목록을 쓰기 때문에 진입 파일에서 불러도 가볍다. 고른 캐릭터의 모델만 게임을 시작하기 전에 받고, 다른 캐릭터는 고를 때 받는다. 받지 못했을 때는 캡슐을 그린다(바꾸는 중에 못 받으면 이전 캐릭터를 그대로 둔다). 모델 파일은 원본 팩에서 변환 스크립트(`scripts/build-characters.mjs`)로 만든다. 어떤 동작을 재생할지는 순수 함수(`render/characterAnimation.ts`)가 정하고, 달리기 동작의 재생 속도는 이동 속도에 비례시킨다.
- **시점**: 좌우·상하 각도는 플레이어 엔티티의 `view` 컴포넌트에 둔다(카메라의 상태가 아니다). 이동 방향이 시점에 달려 있고 플레이어마다 따로 있기 때문이다. 마우스 버튼을 누르고 있는 동안의 마우스 움직임은 입력 단계에서 "이번 틱에 돌릴 각도"(`lookX`, `lookY`)로 바뀌어 행동 값에 실린다. 좌우 각도 0은 -Z를 보는 방향이고 왼쪽으로 돌면 커진다. 상하 각도는 위가 양수다. 카메라의 위치는 캐릭터 위치와 시점에서 계산하는 순수 함수(`render/cameraRig.ts`)로 구한다.

## 9. 구역 시스템

월드는 한 번에 구역 하나만 메모리에 올린다. 구역을 넘어갈 때 이전 구역을 내리고 다음 구역을 불러온다. 이음새 없는 스트리밍은 하지 않는다.

### 9.1 구역의 구성

| 항목 | 초기값 |
|---|---|
| 구역 크기 | 한 변 300~400m. 시제품의 마른 강바닥은 이동 속도를 12 m/s로 올리면서 720m로 넓혔다(끝에서 끝까지 1분은 그대로). 본편의 구역 크기는 플레이 테스트(G1) 뒤에 다시 정한다 |
| 지형 | 구역마다 고정된 하이트맵 1장 |
| 배치 | 건물, 소품, 출입구, 대피 영역, 생성 지점을 구역 정의 파일에 기록 |
| 구역당 내려받는 용량 | 5MB 이하 (공유 에셋 제외) |

구역 전체가 한 번에 화면에 들어올 수 있는 크기이므로 청크 분할, 워커 기반 지형 생성, 원거리 지형 LOD가 필요 없다.

### 9.2 구역 정의

구역은 데이터 파일로 정의한다. 지형과 건물은 고정이고, 내용물은 생성 지점에서 뽑는다.

```json
{
  "id": "dry_riverbed",
  "name": "마른 강바닥",
  "region": "drought_plains",
  "heightmap": "zones/dry_riverbed/height.png",
  "size": 384,
  "exits": [
    { "id": "to_shelter", "to": "shelter", "entry": "from_riverbed", "position": [12, 0, 190] },
    { "id": "to_village", "to": "buried_village", "entry": "from_riverbed", "position": [370, 0, 80] }
  ],
  "prefabs": [
    { "prefab": "ruined_house_a", "position": [140, 0, 210], "rotation": 90 }
  ],
  "travelPoint": { "id": "riverbed_camp", "position": [200, 0, 150] },
  "containers": [
    { "id": "c01", "lootTable": "car_trunk", "position": [98, 0, 176] }
  ],
  "enemySpawns": [
    { "id": "s01", "enemy": "feral_dog", "count": [2, 4], "candidates": [[250, 0, 120], [300, 0, 260]] }
  ],
  "resourceNodes": [
    { "id": "r01", "type": "scrap_pile", "position": [160, 0, 90] }
  ]
}
```

**시제품의 형식.** 위 예시는 전체 게임의 모습이고, 시제품(M1~M2)은 에셋 파일 없이 임시 도형으로 만들므로 더 단순한 형식을 쓴다(`src/world/zoneDefinition.ts`, zod로 검증).

| 항목 | 내용 |
|---|---|
| `id`, `nameKey`, `size` | 구역 ID, 이름의 문구 항목, 한 변의 길이(m) |
| `terrain` | 높이 격자: 한 변의 표본 수 `samples`와 높이 목록 `heights`(북서쪽에서 시작해 한 줄씩, 서→동). 이미지 대신 숫자를 쓰는 것은 브라우저 없이 테스트하기 위해서다 |
| `spawn` | 시작 위치와 바라보는 방향 |
| `buildings` | 건물: 위치, 회전, 크기(폭·깊이·벽 높이), 문이 난 벽과 문 폭, 대피 가능 여부. 프리팹 대신 상자로 만든다 |
| `props` | 소품: 종류(차량, 뒤집힌 차량, 천막, 우물, 장애물), 위치, 회전. 크기는 종류에 따라 코드에서 정한다 |
| `exits` | 출입구: 위치, 막힘 여부, 행선지 구역과 진입 지점 |
| `scatter` | 흩뿌리기: 종류(바위), 개수, 시드 |

- 좌표는 `[동쪽 m, 남쪽 m]`이고 북서쪽 모서리가 원점이다(시제품 설계 5.2와 같다). 월드에서는 `[x, z]`이므로 동쪽이 +X, 북쪽이 -Z다. 높이는 좌표에 넣지 않고 지형에서 구한다.
- 회전은 북쪽 기준 시계 방향 각도다.
- ID는 구역 전체에서 겹치지 않아야 한다. 모르는 항목은 무시하지 않고 거부한다(오타를 잡기 위해).
- 상자, 폭풍 뒤 물건 지점 같은 내용물은 그 기능을 만드는 단계에서 형식에 추가한다.
- 건물 하나는 상자 7개다: 온전한 벽 3개, 문이 난 벽의 양옆 조각 2개와 문 위 조각 1개, 지붕 1개(`src/world/building.ts`). 같은 상자를 화면과 충돌체에 쓴다. 건물 바닥은 따로 만들지 않고, 건물 자리의 지형을 평평하게 고른다.
- 소품은 종류마다 상자 하나이고 크기는 `src/world/props.ts`에 있다. 이 상자가 충돌체다. 모델이 있는 종류(지금은 차량)는 화면에 모델을 그리고 나머지는 상자를 그린다. 어느 소품이 어느 모델을 쓰고 그때의 크기가 얼마인지는 `src/world/propModels.ts`에 데이터로 둔다. 모델이 있는 소품은 상자의 크기도 그 값을 따르므로, 보이는 모양과 부딪히는 범위가 맞는다. 모델은 상자의 길이에 맞춰 같은 비율로 크기를 잡아 상자 자리에 놓는다(`src/render/propModel.ts`). 크기는 팩 안의 사람 대 물건 비율을 따른다(팩의 사람 키 1.52 → 게임의 1.8m). 모델은 구역을 짓기 전에 받고, 받지 못한 소품은 상자로 그린다.
- 소품 모델은 묶음으로 정의한다. 지금은 Quaternius 묶음과, 비교용으로 모델이 없는 묶음(`boxes`)이 있다. 한 소품이 여러 모델로 이루어질 수 있다: 폭을 따라 나란히 놓거나(출구를 막은 컨테이너) 같은 자리에 겹친다.
- 바위는 길을 막는 크기만 모델로 그리고(모델마다 인스턴싱으로 한 번에) 작은 것은 단순한 도형으로 둔다. 모델은 삼각형이 열 배쯤 많은데 작은 바위에서는 차이가 보이지 않기 때문이다.
- **안개는 카메라가 아니라 캐릭터에서부터 센다.** Three.js의 안개는 카메라에서의 깊이로 세는데, 3인칭 카메라는 캐릭터에서 멀리 떨어질 수 있어 그대로 쓰면 시야가 카메라 위치에 따라 달라진다. Three.js의 안개 셰이더 조각(`fog_pars_vertex`, `fog_vertex`, `fog_pars_fragment`, `fog_fragment`)을 갈아 끼워 카메라가 바라보는 지점에서의 거리로 세게 했다(`src/render/sky.ts`). 장면의 `Fog` 객체는 `near`에 그 지점까지의 거리, `far`에 시야를 담는다. **Three.js 버전을 올릴 때 이 조각들의 이름과 쓰임이 바뀌었는지 확인한다.** 직접 만든 셰이더 재질에 안개를 넣을 때도 이 조각들을 쓴다.
- **처음 그릴 때의 끊김을 로딩으로 옮긴다.** 물체는 처음 그려질 때 셰이더를 컴파일하고 도형과 텍스처를 그래픽 카드로 보내는데, 플레이 중에 일어나면 끊김으로 느껴진다(차량 모델에서 최대 200ms를 측정했다). 그래서 구역을 올린 뒤 화면에 보이든 말든 전체를 한 번 그린다(`warmUpScene`). 구역 전환을 만들 때(시제품 2.16)도 새 구역을 올린 뒤 같은 처리를 한다.
- 바위는 구역 정의의 개수와 시드로 흩뿌린다(`src/world/scatter.ts`). 건물, 소품, 시작 지점을 피한다. 화면에는 인스턴싱으로 한 번에 그리고, 길을 막을 만큼 큰 바위에만 충돌체를 둔다.
- 구역의 네 변에는 보이지 않는 벽을 둔다(`src/world/boundary.ts`).
- 구역을 월드에 올리는 일은 `src/world/zoneLoader.ts`가 한다. 올릴 때 만든 충돌체와 메시를 기억해 두었다가 `unload`에서 모두 제거하고 GPU 자원을 해제한다.

- 건물은 **프리팹**(모델 + 충돌체 + 대피 영역 + 내부 컨테이너 자리)으로 만들어 여러 구역에서 재사용한다.
- 바위·잔해 같은 반복 소품은 구역 정의의 밀도 값과 고정 시드로 흩뿌린다. 시드가 고정이므로 모든 플레이어에게 같은 자리에 놓인다.
- 구역을 편집하는 전용 도구는 처음에는 만들지 않는다. 개발용 화면에서 좌표를 찍어 JSON으로 내보내는 정도로 시작한다.

### 9.3 구역 전환

```
출입구 진입 → 화면 가림 → 현재 구역 상태 저장 → 현재 구역 해제
   → 다음 구역 에셋 로드 → 지형·건물·충돌체 생성 → 구역 상태 적용
   → 필요하면 내용물 재생성 → 지정된 진입 지점에 플레이어 배치 → 화면 열림
```

- 목표 전환 시간: 처음 방문 5초 이하, 다시 방문 2초 이하.
- **인접 구역 미리 받기**: 현재 구역에 들어온 뒤 한가할 때 이웃 구역의 에셋을 미리 내려받아 둔다. 메모리에 올리지는 않고 브라우저 캐시에만 둔다.
- 캐릭터, 무기, 공통 소품, UI 같은 **공유 에셋**은 구역이 바뀌어도 해제하지 않는다.
- 게임 시각과 날씨는 전환 중에도 이어진다. 폭풍 속에서 구역을 넘으면 다음 구역도 폭풍이다.
- 빠른 이동도 같은 전환 절차를 쓰고, 추가로 게임 시각을 진행시킨다.

### 9.4 구역 상태와 재생성

구역을 떠나도 그 구역에서 일어난 일은 유지된다.

| 상태 | 내용 |
|---|---|
| 컨테이너 | 열림 여부, 남은 내용물 |
| 자원 지점 | 채집 여부 |
| 적 생성 지점 | 처치 여부 |
| 떨어진 아이템, 사망 시 가방 | 위치와 내용 |
| 플레이어 설치물 | 모닥불, 임시 은신처 |
| 마지막 재생성 시각 | 게임 내 날짜 |

- 구역에 들어올 때 `현재 날짜 − 마지막 재생성 날짜 ≥ 재생성 주기`이면 컨테이너·자원·일반 적을 다시 채운다.
- 재생성 결과는 `(월드 시드, 구역 ID, 재생성 회차)`로 계산한다. 같은 조건이면 같은 결과가 나와 테스트로 재현할 수 있다.
- 두목, 핵심 부품, 플레이어 설치물, 떨어진 가방은 재생성 대상에서 제외한다.
- 플레이어가 없는 구역은 시뮬레이션하지 않는다. 적이 구역을 넘어 따라오지 않는다.

### 9.5 렌더 최적화

| 기법 | 대상 |
|---|---|
| `InstancedMesh` | 바위, 잔해, 마른 나무 등 반복되는 소품 |
| 소품 LOD | 먼 소품은 단순한 모델로 바꾸거나 생략 |
| 안개 | 구역 경계와 먼 풍경을 가림. 날씨 표현과 겸용 |
| 절두체 컬링 | 화면 밖 물체 제외 |
| 재질·텍스처 공유 | 텍스처 아틀라스로 드로우콜 감소 |
| 구역 밖 배경 | 구역 가장자리 너머는 단순한 원경 지형으로 표현 |

## 10. 환경 시스템 (시간·날씨·체온)

날씨와 체온은 이 게임의 핵심이므로 독립된 시스템으로 둔다. 계산은 순수 모듈로 작성하고, 화면 효과는 그 결과를 읽어서 표현한다.

### 10.1 구성

```
게임 시각 ──┐
지역 정보 ──┼─→ 날씨 시스템 ─→ 환경 상태 { 기온, 바람, 시야 거리, 강수, 재난 종류 }
월드 시드 ──┘                        │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
               체온 시스템       AI (행동 변화)    렌더 (하늘·안개·입자·소리)
```

### 10.2 날씨 일정
- 날씨는 `(월드 시드, 지역, 게임 내 날짜)`로부터 계산한 **일정표**를 따른다. 무작위로 그때그때 뽑지 않는다.
- 그래서 저장 파일에는 게임 시각만 있으면 되고, 불러온 뒤에도 같은 날씨가 이어진다. 한파 지대의 날씨 예보 기능도 일정표를 미리 읽는 것으로 구현할 수 있다.
- 날씨 상태: `평상시 → 예고 → 재난 → 잦아듦 → 평상시`. 예고 단계에서 하늘 색과 바람 소리가 먼저 바뀐다.
- 날씨는 지역 단위다. 같은 지역의 구역은 날씨를 공유하므로 구역을 넘어가도 날씨가 이어진다. 대피소 구역은 날씨의 영향을 받지 않는다.

### 10.3 체감 기온과 체온

```
체감 기온 = 지역 기본 기온 + 시간대 보정 + 날씨 보정
          + 열원 보정 (가까운 heatSource)
          − 젖음 보정
          (대피 영역 안이면 날씨 보정과 바람을 차단 정도만큼 감쇠)

목표 체온 = 체감 기온을 복장의 보온·통풍으로 보정한 값
체온     = 목표 체온을 향해 일정 속도로 이동
```

- 체온은 즉시 바뀌지 않고 서서히 따라간다. 잠깐 폭풍 속을 뛰는 것은 가능하지만 오래 버티지는 못한다.
- 체온 계산은 플레이어 한 명만 대상이므로 매 틱이 아니라 초당 몇 회만 갱신한다.

### 10.4 대피 판정
- POI 건물과 임시 은신처에 `shelterZone` 영역(박스)을 둔다. 플레이어가 영역 안에 있는지만 검사한다.
- 지붕 유무를 레이로 검사하는 방식은 쓰지 않는다. 영역 방식이 가볍고 결과를 예측하기 쉽다.

### 10.5 화면 표현

| 요소 | 방법 | 부하 |
|---|---|---|
| 하늘과 햇빛 | 시각·날씨에 따라 하늘 색, 조명 색과 세기를 보간 | 거의 없음 |
| 시야 감소 | 안개 거리와 색 조절 (모래폭풍, 눈보라) | 가시거리가 줄어 오히려 그릴 양이 감소 |
| 입자 (모래, 비, 눈) | 카메라 주변에만 생성하는 `Points` 한 묶음 | 입자 수를 품질 프리셋으로 조절 |
| 더위 표현 | 화면 가장자리 색 변화. 높음 품질에서는 아지랑이 왜곡 후처리 추가 | 후처리는 높음 품질에서만 |
| 소리 | 바람·비 소리를 날씨 세기에 맞춰 교차 재생 | — |

날씨는 이 게임의 핵심 볼거리다. 모바일 제약이 없어졌으므로 높음 품질에서는 후처리(아지랑이, 블룸, 대기 산란)를 적극적으로 쓸 수 있다. 다만 최소 사양에서도 날씨가 무엇인지는 분명히 전달되어야 한다.

## 12. 저장

### 저장 내용

| 구분 | 내용 |
|---|---|
| 메타 | 세이브 버전, 월드 시드, 플레이 시간 |
| 플레이어 | 위치, 능력치(체온·젖음 포함), 가방, 장비, 레벨, 퍽, 해금 레시피 |
| 월드 | 게임 내 시각, 대피소 보관함, 설치한 모닥불·은신처 |
| 진행 | 대피소 시설 복구 단계, 처치한 두목, 개방된 지역, 활성화한 이동 거점, 현재 구역 |
| 구역 상태 | 구역별 컨테이너·자원·적 상태, 떨어진 아이템, 설치물, 마지막 재생성 날짜 (9.4) |

날씨는 저장하지 않는다. 게임 내 시각과 시드로 다시 계산한다(10.2).

### 방식
- IndexedDB에 저장. 구역 상태는 구역 ID를 키로 따로 저장해 한 번에 쓰는 양을 줄인다.
- 자동 저장: 구역을 넘어갈 때, 대피소에 들어갈 때, 일정 주기, 탭이 가려질 때.
- 계정이 없으므로 저장은 브라우저에만 남는다. 브라우저 데이터를 지우면 사라진다는 점을 설정 화면에 알리고, 저장 파일 내보내기/가져오기를 제공한다.
- **세이브 버전 관리**: 스키마가 바뀌면 버전을 올리고 `v1 → v2` 변환 함수를 추가한다. 장기 프로젝트에서 기존 세이브가 깨지는 것을 막는다.

## 13. UI

- 캔버스 위에 DOM을 겹쳐 UI를 그린다. 글자 렌더링, 스크롤, 마우스 입력 처리를 브라우저에 맡길 수 있다.
- 매 프레임 바뀌는 값(체력 바 등)은 Preact 렌더를 거치지 않고 DOM을 직접 갱신해 부하를 줄인다.
- 창 크기와 화면 비율(16:9, 16:10, 울트라와이드)이 달라도 배치가 깨지지 않게 한다.
- 모든 화면은 키보드/마우스와 게임패드 양쪽으로 조작할 수 있어야 한다.

| 화면 | 내용 |
|---|---|
| HUD | 체력/스태미나/허기/갈증/체온, 빠른 사용 슬롯, 상호작용 안내, 시각, 날씨 경고 |
| 인벤토리 | 가방 격자, 복장·무기 슬롯, 아이템 상세(보온·통풍 포함) |
| 제작 | 레시피 목록, 필요 재료, 제작 버튼 |
| 컨테이너 | 컨테이너 내용 ↔ 가방 |
| 대피소 | 시설별 복구 단계, 필요 재료, 복구 버튼 |
| 일시정지와 설정 | 계속하기, 설정, 조작 방법. 설정 항목은 [게임 기획서](01-게임기획서.md) 15장 |

### 13.2 언어

- 지원 언어는 영어와 한국어다. 처음에는 브라우저 언어를 따르고 설정에서 바꾼다.
- 화면의 모든 글자는 **문구 파일**에서 가져온다. 코드와 데이터 파일에 글자를 직접 쓰지 않는다.

```
Src/src/locales/en.json    { "hud.storm_warning": "Storm approaching", "item.water.name": "Water bottle" }
Src/src/locales/ko.json    { "hud.storm_warning": "폭풍이 다가옵니다", "item.water.name": "물병" }
```

- 문구에 값을 끼워 넣을 수 있다(예: `"{count}개 획득"`). 언어마다 어순이 달라도 되게 문장을 이어 붙이지 않는다.
- 두 파일의 항목이 빠짐없이 일치하는지 단위 테스트로 확인한다. 빠진 문구가 있으면 빌드 검증이 실패한다.
- 언어를 바꾸면 화면을 다시 불러오지 않고 바로 반영한다.
- 별도 번역 도구는 쓰지 않는다. 문구가 수백 개 수준이라 간단한 함수 하나로 충분하다.
- 시작 언어는 다음 순서로 정한다: 주소의 `?lang` → (설정에 저장한 언어, 시제품 2.22부터) → 브라우저의 첫 번째 선호 언어 → 영어. 지원하지 않는 값은 건너뛴다.
- 없는 항목을 요청하면 항목 이름을 그대로 화면에 보여 주고 콘솔에 오류를 항목당 한 번 남긴다. 끼워 넣을 값이 빠지면 `{count}` 같은 자리 표시를 그대로 둔다. 둘 다 화면에서 바로 눈에 띄게 하기 위해서다.
- 항목의 기준은 영어 파일이다. 코드에서 쓰는 항목 이름은 영어 파일에서 타입으로 뽑으므로, 없는 항목을 쓰거나 한국어 파일에 항목이 빠지면 타입 검사에서 걸린다. 단위 테스트는 남는 항목, 빈 문구, 끼워 넣는 값의 이름이 언어마다 같은지도 확인한다.

### 13.3 설정의 보관

- 설정은 `localStorage`에 게임 저장과 별도로 보관한다. 게임 저장(IndexedDB)을 지우거나 가져와도 설정은 바뀌지 않는다.
- 설정에도 버전을 붙인다. 항목이 늘거나 바뀌면 이전 값을 새 형식으로 옮기고, 읽을 수 없는 값은 기본값으로 대체한다.
- 설정 값은 한 곳(설정 저장소)에서 관리하고, 렌더러·소리·입력·UI가 변경을 구독해 즉시 반영한다.
- 그래픽 품질 "자동"은 처음 몇 초 동안의 프레임을 보고 프리셋을 고른다.

## 15. 성능 예산

| 항목 | 최소 사양 (낮음 품질) | 권장 사양 (높음 품질) |
|---|---|---|
| 기준 기기 | 내장 그래픽 노트북 | 외장 그래픽 PC |

| 후처리 | 없음 | 블룸, 아지랑이, 대기 효과 |
| 동시 활성 적 | 15 | 30 |
| 날씨 입자 | 3천 개 이하 | 2만 개 이하 |
| 첫 화면까지 내려받는 용량 | 10MB 이하 | 좌동 |
| 구역 전환 시간 | 처음 5초, 재방문 2초 이하 | 좌동 |

재난 날씨 중에도 프레임 기준을 지켜야 한다. 날씨가 가장 긴박한 순간이므로 이때 끊기면 안 된다.

- **품질 프리셋**(낮음/중간/높음)으로 가시거리, 그림자, 해상도 배율, 소품 밀도를 묶어서 조절한다.
- **동적 해상도**: 프레임이 떨어지면 렌더 해상도를 자동으로 낮춘다.
- 매 프레임 객체를 새로 만들지 않도록 벡터 등은 재사용한다(가비지 컬렉션으로 인한 끊김 방지).
- 개발 중 화면에 FPS, 드로우콜, 삼각형 수, 현재 구역, 구역 전환에 걸린 시간을 항상 표시한다.
- **성능 측정 기능**을 게임에 넣는다: 개발용 성능 HUD(FPS, 프레임 시간, 구간별 시간, 자원 수), 정해진 경로를 자동으로 돌며 측정하는 성능 측정 모드(`?bench`), 플레이어용 FPS 표시. 자세한 내용은 [시제품 개발 계획](05-시제품개발계획.md) 2.4절에 있다.
- FPS는 모니터 주사율에 막히므로 여유를 보려면 프레임 시간(ms)을 함께 본다.

## 18. 멀티플레이 대비

멀티플레이는 수직 슬라이스 이후에 추가한다. 지금은 네트워크 코드를 만들지 않는다. 다만 **싱글플레이 전용으로 짠 게임에 멀티플레이를 나중에 붙이는 것은 게임 개발에서 가장 비용이 큰 변경 중 하나**이므로, 구조만은 처음부터 맞춰 둔다.

### 18.1 가정하는 형태

| 항목 | 가정 |
|---|---|
| 형태 | 친구끼리 하는 2~4인 협동. 대전과 대규모 접속은 다루지 않음 |
| 방식 | 한 명의 브라우저가 방장이 되어 게임을 진행하고, 나머지가 접속 (방장 권한 방식) |
| 연결 | 브라우저 간 직접 연결(WebRTC). 연결을 맺어 주는 작은 중계 서버만 필요 |
| 동기화 | 방장이 적·날씨·컨테이너의 결과를 정하고 상태를 보냄. 각자의 캐릭터 움직임은 자기 화면에서 먼저 반영 |

전용 게임 서버를 두지 않는 방식을 가정한 이유는 운영 비용 때문이다. 무료 웹 게임에서 서버 비용은 지속적인 부담이 된다. 형태가 달라지면(대전, 모르는 사람과의 매칭) 이 가정은 맞지 않고 전용 서버가 필요해진다.

### 18.2 지금부터 지킬 원칙

이 원칙들은 대부분 싱글플레이에서도 좋은 구조이고, 추가 비용이 거의 들지 않는다.

| # | 원칙 | 이유 |
|---|---|---|
| 1 | **"플레이어"를 전역 변수 하나로 두지 않는다.** 시스템은 `player` 컴포넌트를 가진 모든 엔티티를 처리한다 | 나중에 플레이어가 여럿이 되어도 시스템을 고치지 않는다 |
| 2 | **입력과 시뮬레이션을 분리한다.** 시뮬레이션은 키보드가 아니라 "이 플레이어의 행동 값"을 읽는다 | 원격 플레이어의 행동 값을 네트워크에서 받아 같은 자리에 넣을 수 있다 |
| 3 | **월드를 바꾸는 일은 모두 명령을 거친다.** 상자 열기, 줍기, 제작, 설치, 시설 복구 | 명령이 그대로 네트워크 메시지가 된다. 방장이 명령을 검증하고 결과를 알린다 |
| 4 | **게임 상태는 직렬화할 수 있는 데이터로 둔다.** 저장 기능을 위해 이미 필요하다 | 저장 파일의 형식이 접속한 사람에게 보내는 초기 상태가 된다 |
| 5 | **난수는 시드를 받는 생성기만 쓴다.** `Math.random()`을 게임 로직에 쓰지 않는다 | 방장만 결과를 정하고, 필요하면 재현할 수 있다 |
| 6 | **카메라, UI, 소리는 "내 캐릭터"를 가리키는 값 하나를 통해서만 플레이어에 접근한다** | 화면의 주인공이 누구인지가 한 곳에서 정해진다 |
| 7 | **게임이 멈춘다는 가정에 의존하지 않는다.** 메뉴를 열어도 시뮬레이션은 돌 수 있어야 한다 | 여럿이 하면 멈출 수 없다 |
| 8 | **엔티티에 안정적인 ID를 준다.** 구역 정의의 ID(`c01`, `s01`)와 실행 중 생성되는 ID를 구분한다 | 양쪽이 같은 대상을 가리킬 수 있어야 한다 |

### 18.3 나중에 풀어야 할 문제

대비해도 남는 일이다. 멀티플레이를 추가할 때의 작업 목록이 된다.

| 문제 | 내용 |
|---|---|
| 물리 결과의 차이 | 물리 엔진의 결과는 기기마다 미세하게 다를 수 있다. 같은 입력을 재생하는 방식이 아니라 상태를 주기적으로 맞추는 방식을 써야 한다 |
| 지연 보정 | 내 캐릭터는 먼저 움직이고 나중에 방장의 결과와 맞춘다. 적과 다른 플레이어는 약간 과거의 위치를 부드럽게 보여 준다 |
| 공격 판정 | 내 화면에서 맞았는데 방장 쪽에서는 빗나간 경우의 처리 |
| 구역 | 일행이 서로 다른 구역에 있으면 방장이 여러 구역을 동시에 진행해야 한다. 일행이 함께 이동하게 하면 피할 수 있다 |
| 시간 건너뛰기 | 수면과 빠른 이동의 시간 경과를 여럿일 때 어떻게 할지 (기획서 14장) |
| 방장 이탈 | 방장이 나가면 게임이 끝나는가, 다른 사람이 이어받는가 |
| 저장의 주인 | 진행 상황이 방장의 것인가, 각자의 것인가 |
| 연결 실패 | 일부 네트워크 환경에서는 직접 연결이 되지 않아 중계 서버가 데이터까지 전달해야 한다. 이 경우 비용이 발생한다 |
| 부정행위 | 방장 권한 방식에서는 방장이 조작할 수 있다. 친구끼리 하는 협동에서는 감수한다 |

### 18.4 구조 확인 실험 (권장)

원칙을 지켰는지는 실제로 연결해 봐야 안다. 콘텐츠가 많아진 뒤에 문제를 발견하면 고칠 양도 많아진다.

- **내용**: 브라우저 두 개에서 캐릭터 두 명이 같은 구역을 돌아다니고, 한쪽이 상자를 열면 다른 쪽에도 열린 것으로 보이는 것까지.
- **시점**: G1 통과 후, 전투(M3)를 만들기 전을 권한다. 며칠 분량의 실험이며 결과물은 버려도 된다.
- **목적**: 멀티플레이를 만드는 것이 아니라, 18.2의 원칙이 실제로 통하는지 확인하는 것.
